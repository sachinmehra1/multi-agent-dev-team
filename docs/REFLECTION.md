# Module 5 reflection — retrospective on the current Coder prototype

**Author's preparation draft — 2 November 2026**  
**Scope note:** This reflection describes implementation decisions documented in the current repository, not a falsely claimed completed three-agent Module 5 system. It should be reviewed and personalized before academic submission.

## Three consequential design decisions

The first major choice was to use a LangGraph `StateGraph` with typed Pydantic state rather than a single prompt or unconstrained Python loop. The graph in `orchestration/graph.py` has explicit `think`, `act` and `finalize` nodes, with conditional transitions for a tool action, another reasoning attempt or finalization. That makes safety rules visible in the control flow. The ten-model-call budget is stored in `AgentState` while LangGraph independently enforces a recursion limit of 40. Keeping these separate is important: a tool cycle may consume multiple graph steps but only one model call. The model can also return invalid JSON and require a repair call without touching a tool. An ordinary while loop could achieve these outcomes, but making the transitions explicit improves reviewability and provides a clear integration point for future PM and QA nodes. The trade-off is framework complexity and dependency management. This choice is documented in the current graph, README and architecture note.

The second decision was to combine two kinds of memory. `ConversationMemory` stores the last N request-observation exchanges, while `SemanticMemory` persists task and action observations in Chroma and filters retrieval by session. The task is pinned separately, so sliding-window trimming does not delete the active objective. Importantly, `think` retrieves semantic memories before each model call, including a call made to repair an invalid JSON response. This choice reduces context growth while allowing the system to recover relevant earlier constraints. Its downside is that memories retrieved from prior model-generated observations may be inaccurate or malicious. The implementation therefore labels recalled material as untrusted rather than allowing it to override system instructions. The existing tests demonstrate recall and session isolation, but a broader semantic-quality benchmark has not been recorded.

Third, I prioritized execution integrity and isolation over convenience. The model never executes code with Python `eval` or `exec` in the orchestrator. Instead, `ToolRegistry` validates arguments; `FileTools` restricts workspace paths; and `CodeRunner` sends a bounded snapshot to a fresh, restricted Docker container. An edit resets the execution result, and `finalize` will not claim success when the latest code has not passed an execution check. This prevents a model's confident final message from being mistaken for test evidence. It does not prove program correctness, because a generated script can have weak tests. The design also introduces Docker startup time, operational prerequisites and a sensitive host Docker socket in the trusted Compose orchestrator. This is a deliberate security and usability trade-off that needs further hardening for production.

## Hardest documented bug and its resolution

The clearest verifiable failure appears in the 26 October 2026 verification record and commit `e80af509fa119d330768ff67855146acc34cc32d`. Early live attempts generated and executed correct code but then failed validation of the final `Decision` structure, including the single permitted format-repair attempt. In other words, the underlying code task could succeed while the overall workflow still returned an invalid final structure. The response was not to weaken validation or remove the iteration cap. Instead, the system prompt gained a concrete, correctly shaped `finish` example with the four exact `final` fields, and the repair pathway began returning field-level Pydantic errors without echoing sensitive raw exception data. A regression test checks that the repair feedback includes the offending field and error type. The later verification record reports a successful real-model addition task with three iterations and 3,754 provider-reported tokens. This evidence demonstrates a change and a successful later run; it does not by itself quantify developer hours lost or prove that the original code was AI-authored.

## What I would do differently

If I were starting again, I would build a minimal three-agent PM-to-Coder-to-QA vertical slice before polishing the standalone Coder. The current repository has strong Coder-specific evidence but PM and QA remain stubs, a serious gap against Module 5's 40%-weighted functionality criterion. I would introduce an explicit typed PM specification and QA verdict, then write integration tests that force real handoffs and bounded QA-driven rework. I would also design a single physical-request counter before adding network retries, so each retry respects the ten-call budget and provider token usage is captured consistently.

I would collect performance data from the beginning: model, agent role, input/output tokens, latency, cost assumptions, first-pass QA acceptance and per-task success. That would allow an honest before/after optimization rather than a retrospective guess. Finally, I would automate an API-documentation build, run Compose from a clean checkout in CI, and maintain a structured prompt/verification log for every AI-assisted change. These changes would make the system easier to reproduce, defend and evaluate. They are priorities for the remaining Module 5 work, not features I can claim are implemented today.
